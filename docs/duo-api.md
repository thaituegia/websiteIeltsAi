# Shared IELTS learning path

Two fixed authenticated accounts belong to one `duoId`, with the roles `husband` and `wife`. Phone credentials are provisioned separately by the authentication module; this file contains no account secrets. The ordinary content library, mock exams, vocabulary, personal assessment and practice routes remain independently available to each account.

`server/duo.ts` exports `createDuoService(database, config?)`. The service uses the application's existing MongoDB connection. Its indexes are initialized once, before its first member operation; `initialize()` can also be awaited explicitly at startup. Config comes from server code, never request bodies. Defaults are 20 sessions per band, gates after sessions 5/10/15, a 70-percent objective gate threshold, a 5-second promotion countdown, 30-second heartbeat freshness, 120-second Ready freshness, and 20-second countdown-start grace. `gateInterval` supports 5 or 10; session count, pass threshold and strict retake can be configured by the server. `sessionsByBand`, such as `{ "7.5": 20, "8": 30 }`, overrides individual bands; each count must be at least the gate interval and at most 100. The actual lesson list carries each band’s persisted count, while `sessionsPerBand` is the default. Later configuration changes do not rewrite an existing path.

## Placement and persistence

The backend records only completed, server-assessed placement attempts owned by the authenticated member. Existing completed placements are imported idempotently when the shared path is first viewed. Normal onboarding waits until both members have completed placement. Its starting band is the lower result, rounded to the existing half-band scale and bounded by 3.0 and 8.0. Later placements remain in history and update personal estimates without resetting or promoting the shared path. An explicit owner request can instead use the [offline band-3 operator](duo-band-assignment.md); it assigns a starting rank without inventing a placement score.

`duo_learning_paths` contains the one canonical document per Duo. It embeds band progress, member completion proofs, retained gate results and retained promotion results. Both members read the same `currentBand`; the backend never writes the shared band into their personal `users.currentBand`. Each transition is a compare-and-swap replacement against the document's revision. Both valid promotion passes and the next-band unlock are committed in that single atomic update, including on standalone MongoDB where transactions are unavailable. Separate `duo_placement_results`, `duo_assessments`, and `duo_promotion_rooms` preserve placement history, every assessment receipt, room state, and all retakes. A restarted application uses the same persisted records.

## JSON API

All routes use the existing authenticated session middleware. Route IDs should be URL encoded.

| Method | Route                           | Body and result                                                                                                                                                                    |
| ------ | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/duo`                      | `{duo: DuoSnapshot}` from `shared/duo.ts`; member names, personal placements, shared band, lesson progress, gates, latest room and up to 100 most recent own assessment summaries. |
| POST   | `/api/duo/lessons/:id/complete` | `{attemptId}` or `{cardIds}` for a configured vocabulary session; returns `{duo}` after proof validation.                                                                          |
| POST   | `/api/duo/gates/:id/start`      | Opens/resumes an owned eligible assessment and returns `{assessment}`. Passed results are retained.                                                                                |
| GET    | `/api/duo/assessments/:id`      | Returns only the authenticated owner's `{assessment}`, reconciling current server grades.                                                                                          |
| POST   | `/api/duo/rooms`                | Opens/resumes the shared eligible promotion room; returns `{room}`.                                                                                                                |
| GET    | `/api/duo/rooms/:id`            | Returns `{room}` with `serverNow`, presence, countdown, common start and deadline.                                                                                                 |
| POST   | `/api/duo/rooms/:id/join`       | Joins/rejoins as the authenticated member; returns `{room}`.                                                                                                                       |
| POST   | `/api/duo/rooms/:id/heartbeat`  | Refreshes only the authenticated member's presence; returns `{room}`.                                                                                                              |
| POST   | `/api/duo/rooms/:id/ready`      | `{ready: boolean, companion?: boolean}`; returns `{room}`.                                                                                                                         |
| POST   | `/api/duo/rooms/:id/leave`      | Clears the member's presence and Ready; cancels an unstarted countdown.                                                                                                            |
| POST   | `/api/duo/rooms/:id/start`      | After the server countdown returns `{room, assessment, companion}`. A companion's assessment is `null`.                                                                            |

The API does not accept a score, shared band, gate-pass checkbox, membership role, partner identity, threshold or client clock. Assessment summaries do not disclose partner responses, private recordings, answer keys or feedback. Individual result detail remains in the existing owned attempt endpoint. All stored assessment receipts remain retrievable through paginated own history and by owned ID, even when they no longer appear among the latest 100 summaries.

## Lesson and gate proofs

Default sessions rotate Reading, Listening, Writing, Speaking and Grammar, four times per band. Each references an existing content item; all existing content remains in the public bank. Completing a session requires an owned submitted attempt for exactly that content, server feedback, and a submission at or after that band was unlocked. Objective sessions require answers to at least 80 percent of actual question slots; Writing requires each actual task to reach 150 words for Task 1 or 250 words for Task 2; Speaking requires a nontrivial transcript (30 words, 12 distinct words), or an owned saved recording. Lesson completion records study effort; it does not manufacture a band or AI grade. Configured vocabulary sessions instead require the user's own reviewed cards for every assigned vocabulary item, with genuine server review logs at or after unlock. An arbitrary completion checkbox or a partner's attempt never suffices.

Within an unlocked segment the members study independently. A gate becomes eligible only when both have completed the required preceding lessons and earlier gates are open. Each member can take it at any time, without the other online. Both must independently meet the gate's pass rule; a valid pass is retained while the partner retries. Gate results do not change the shared band. Ordinary practice on a locked path item's content is still allowed, but cannot bypass the shared lesson or gate requirements.

## Promotion rooms and independent attempts

Both must finish the current band and all gates before creating a promotion room. Each must join and Ready using their own authenticated account. A single join or Ready cannot start it. The server checks fresh presence and Ready state, starts a common countdown, and cancels stale/abandoned countdowns. A countdown observed too late is reset rather than silently starting an absent participant. At a valid start the service creates all required owned assessments with a common room start and end, even if the partner's UI has not clicked the start button yet.

Reading, Listening, Writing and Speaking use existing full mocks. Their section start times and deadlines derive from the common room start and the actual content durations. A future section cannot open early, prior sections must be submitted, and a late join/reload never extends a deadline. After a legitimate common start, temporary disconnection does not invalidate recorded answers: the same member may rejoin and resume within the original time. The browser should heartbeat approximately every 10 seconds while in a room or promotion attempt.

For gates, objective components pass at the configured percentage. For promotion, **every one of the four skills must reach the next half-band** (capped at 8.0), using Reading/Listening server reference-band estimates and actual AI Writing/Speaking assessments. An average across partners or a 70-percent shortcut cannot promote a 7.5 path to 8.0. Productive work with rule-based fallback, absent AI band, or an unfinished provider result stays `pending-ai`, including after the exam timer. It never counts as pass. Submitted blank productive work without any saved recording fails, so an empty submission cannot leave a room permanently waiting for an impossible AI result. An owned recording saved before the deadline remains pending until its real STT and acoustic assessment are available. The application's owned regrading route may supply a real provider result later; reconciliation then updates the assessment. Each member's pass remains independent.

Promotion Writing requires meaningful work for every task declared by its full mock: at least 150 words for Task 1 and 250 for Task 2. A missing or unfinished required task fails even if another task has a high AI score. All required tasks must also have real server AI task scores; a receipt missing a required task score stays `pending-ai` and cannot promote. Ordinary single-task practice and its lesson proofs retain their existing rules.

When saved work is actively being graded at a deadline, the server's live submission lease keeps that part and room in progress. A new room cannot displace the accepted work while the provider result is still pending. The lease contains a server-only token and expiry; it is never exposed in attempt views. A valid late grading result can complete the original assessment, while an abandoned or expired lease falls back to the normal failed-deadline rule and allows a retake.

Default retakes preserve a passed member's valid result within the current band. A new room still requires both present and Ready, while that member may choose Companion and the other retakes all required parts. Failed new scores do not erase a retained pass in this default mode. With `strictRetakeMode`, opening a new room clears both current promotion passes, both must retake, and an older room's receipt cannot satisfy the new attempt. Progress never exceeds 8.0. Previously unlocked lessons and all ordinary practice remain available for revision.

## Hooks in existing attempt/placement handlers

1. `beforeAttempt(user, {contentId, mode, duoAssessmentId?})` returns `{duoAssessmentId?, deadlineAt?, existingAttemptId?}`. Omitted context means unrestricted ordinary practice. A protected assessment must use `exam`, belong to that user, contain that content, satisfy backend prerequisites, and for promotion originate from a valid started room. An already-bound part must return its same owned attempt rather than inserting another.
2. Store the returned `duoAssessmentId` and server `deadlineAt` on the ordinary attempt. Call `bindAttempt(user, attemptId, assessmentId?)` after insertion/resumption to bind only that owned protected attempt to its assessment part. An unrelated open regular exam cannot be reused as a Duo result; the application returns 409 and asks the member to finish it first.
3. After server grading persists an attempt, call `attemptSubmitted(record)`. Repeat this for already-submitted reads and real provider regrading; it is idempotent. Neither body fields nor ordinary unbound attempts can supply a Duo pass.
4. After placement grading persists its completed record, call `placementCompleted(user, record)`. The hook reads and validates the owned stored record again.

`tests/duo.test.ts` exercises these rules against separate disposable native MongoDB databases, including concurrent receipts, placement races, unauthorized proof reuse, gate bypass, countdown expiry/rejoin, pending AI, companion retakes, strict retakes, and the 8.0 cap. Productive grades in tests are explicitly synthetic server receipts; these tests do not claim to call or calibrate an external AI provider.
